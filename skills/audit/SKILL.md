Audit the Claude Code setup that applies when working in the current directory. Compare it with Anthropic's current published guidance. The deliverables are a report and a proposed diff. This audit is read-only: the report is the only file that should remain when you finish (see **Temporary files**). The person applies the hunks they choose.

## Rules

- **Evidence.** Every finding cites `file:line` and quotes the line. It also cites what the line conflicts with, matched to the kind of claim:
  - **Product behavior** (what Claude Code or a model does): the official docs page, by URL, with a short quote.
  - **A local inconsistency** (a stale path, two files that disagree): the contradicting repository `file:line`, quoted.
  - **A prompt-audit pattern or recommendation**: the guide, identified as `claude-api` skill, `shared/prompt-audit.md`, with its section or row, and the Claude Code version it came with.

  A claim that a setting, field, command or feature does not exist needs two independent checks, for example the docs page plus `claude --help` or a string search of the installed binary. Show both checks.
- **Sources.** For product behavior, Anthropic's own docs are the only reference; the bundled `prompt-audit.md` counts as Anthropic's for the patterns it defines. Blog posts, threads and third-party skill packs are not references, even when they quote Anthropic.
- **Privacy.** Write `[hidden]` in place of any secret, token, key or email address. Fetch only the documentation URLs. Send no project content to any outside service. Redaction keeps secrets out of the report and the chat; it doesn't keep them out of your context. Reading a file puts its values in your context, and a credential recognized only by its content has been read before it can be recognized. Validate this skill with synthetic secrets, never real credentials.
- **No side effects.** Run only commands that read. Some tools change state when they run, for example a skill manager that updates itself or syncs on `list`, so use their offline or read-only flags. If a tool has no such flag, read its files instead of running it. Run `git status` as `git --no-optional-locks status`, so git doesn't rewrite its index.
- **Temporary files.** Read fetched pages without saving them where you can: the fetch tool, or `curl -s <url>` to standard output. If you need files, make one folder for this run with `mktemp -d` and keep a list of every file you create in it. When the findings are complete and before you write the report, delete exactly those files and then the empty folder (`rm -- <file> …`, then `rmdir <folder>`); don't delete recursively. That way the report records what is actually left. If a delete is blocked or fails, for example because of a guard hook, don't work around it and don't ask the person to delete anything: list the leftover paths and what blocked them under "Not checked" and in the chat summary.
- **Managed files.** Some files are written or regenerated by tools: skills installed by a skill manager (look for its marker or lock file, such as `skills-lock.json`), the plugin cache (`~/.claude/plugins/`), and symlinks that point outside `~/.claude`, for example into a Nix store or a dotfiles repo. Report findings in these files, but propose no edits to them. Name the upstream source to change instead.
- **Config directory.** `~/.claude` in this skill means Claude Code's config directory: the `config-dir=` argument when one is given, else `$CLAUDE_CONFIG_DIR` when it is set, otherwise `~/.claude`.

## How this skill uses prompt-audit.md

Step 4 follows the `claude-api` skill's `shared/prompt-audit.md`, steps 1–4, and step 6 uses its step 5 finding fields and confidence rubric and its step 6 diff rules. Its step 7, behavioral verification, is not part of this skill. The rest of that guide applies as written, except for these five instructions:

1. **Target model** (its step 0, item 2: audit configuration files "against the model the request names, else the model running this audit"). Step 1 of this skill replaces that order. The guide's rule that a skill, subagent or command pinning its own model is audited against that model still applies.
2. **Settings files and hook definitions** (its step 1: they "can hold secrets - do not read them"). That rule still governs the prompt-text audit in step 4. Other steps of this skill read `~/.claude/settings.json`, `.claude/settings.json` and `.claude/settings.local.json`, for these keys only: step 1 for `model`; step 2 for hook commands, `enabledPlugins` and `skillOverrides`; step 5 for the keys, values and hook definitions it checks; step 6 for `enabledPlugins`. Never copy a secret value into notes, chat or the report: name it by key path and write `[hidden]`. Treat as secret every value under `env`, `headers` or `apiKeyHelper`, and any value whose key or content looks like a credential. `.mcp.json` and credential files stay unread. List them by path only, and give "not read; line count not measured" in place of the line count step 2 asks for.
3. **Symbol checks** (its Group 2 "Volatile specifics" row: make checks "with the file-reading tools, not shell commands"). Check that a named path exists with the file-reading tools, without following symbolic links, as the guide says. To check that a command, flag, function or type named in an instruction file is still defined, you may search the project with `git grep -n -F '<name>'`, or `grep -rn -F` when there is no repo. Search for the name only, inside the project, and run nothing you find.
4. **Report layout** (its step 5: one list ordered by confidence, and for a clean surface a one-line verdict with "nothing else"). The report follows this skill's layout in step 6, which always includes the inventory and references. Step 4's findings keep the guide's shape and order; step 5's configuration findings go in a section of their own.
5. **Applying edits** (its step 6: apply edits "when the request itself explicitly asked for the changes to be applied"). This skill never applies edits; it writes the proposed diff and stops.

**If the guide is missing or has changed.** Before step 4, check that `shared/prompt-audit.md` exists and that each phrase quoted in the list above still appears in it. If the file is missing, or a quoted phrase is gone or reworded:

- Say so at the top of the report: name the missing file, or each instruction that no longer matches, and the Claude Code version.
- Apply this skill's own scope and rules as written. Don't reinterpret them to fit the new text.
- Mark each check that depends on a missing or mismatched instruction "unverified", in its findings and under "Not checked". Don't describe the audit as following the guide where it no longer can.

When the whole guide is missing, step 4 audits against the fetched prompting guide alone, and every step 4 finding is marked unverified against prompt-audit patterns.

## Steps

### 1. Scope and target model

- **Arguments** (`$ARGUMENTS`), all optional: a target model, `config-dir=<path>` (see **Config directory**) and `report-dir=<path>` (see step 6).
- **Project root:** the output of `git rev-parse --show-toplevel`, or the current directory when there is no repo.
- **Target model**, resolved in this order:
  1. the target model argument
  2. `model` in `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`
  3. the model running this session

  State the target model at the top of the report. Also list every model that an agent or skill file pins.

Done when the project root and the target model are both stated.

### 2. Inventory

List every file that reaches the model or configures the harness. Give each file's line count, and mark when it loads: **always** (every session) or **on trigger**.

- **User layer:**
  - `~/.claude/CLAUDE.md`, plus the files it `@`-imports
  - `~/.claude/settings.json`
  - `~/.claude/CLAUDE.local.md` and `~/.claude/settings.local.json`, if present, marked **not loaded**. Claude Code reads `CLAUDE.local.md` only from the working directory and its ancestors, and reads `~/.claude/settings.local.json` only as local settings for sessions started in `~` itself. Audit them as part of the project only when the project root is `~`.
  - `~/.claude/agents/`, `skills/` (including claude.ai-synced skills under `skills/synced/`), `commands/`, `rules/` and `output-styles/`
  - every hook script that the settings files reference
  - the auto-memory folder for this project: `~/.claude/projects/<project-path-slug>/memory/`
- **Project layer:**
  - `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md` at any depth outside dependency folders, plus `.claude/CLAUDE.md`
  - `CLAUDE.md` and `CLAUDE.local.md` in every directory above the project root, such as `~/CLAUDE.local.md`; these load too
  - `.claude/settings.json` and `settings.local.json`
  - `.claude/agents/`, `skills/`, `commands/` and `rules/`
  - `.mcp.json`
- **Plugins:** enabled plugins and the count of skill descriptions that each one adds. List these only. Don't audit plugin bodies.

Then measure the always-loaded text, in characters, as three figures: the CLAUDE.md chain, the memory index, and the skill descriptions. The skill figure is an **observable subtotal**, defined as follows:

- **Included:** the `name` and `description` of every model-invocable skill on disk: user skills (`~/.claude/skills/`, including `synced/`), project skills (`.claude/skills/`), and the skills of each plugin that `enabledPlugins` turns on, from that plugin's installed folder under `~/.claude/plugins/cache/`.
- **Excluded:** skills with `disable-model-invocation: true`, and skills that a `skillOverrides` entry sets to `"off"` or `"user-invocable-only"`. For `"name-only"`, count the name only.
- **Deduplicated:** count a `SKILL.md` reached by two paths, such as a symlink, once. When two skills share a name, count both and report the clash.
- **Partial:** skills bundled with Claude Code, and any skill not on disk, can't be inspected. Name each source left out, label the figure "observable subtotal (partial)", and never present it as the runtime total.

Done when every path above is either listed or marked absent, and the three figures are stated.

### 3. Fetch the references

Use the Claude Platform docs MCP server only when you can identify it the way the `claude-api` skill's `shared/live-sources.md` documents: its `search_docs` and `get_doc` tools belong to a server whose name contains `claude-platform`. A docs tool from any other server doesn't count. Otherwise, or if a call fails, fetch the `.md` URLs below directly. Record the fetch date for each page.

- **Prompting guide for the target model.** Find its URL in the `claude-api` skill's `shared/live-sources.md`. If that file has no entry for the target model, find the "Prompting Claude <model>" page in the Claude Platform docs index at `https://platform.claude.com/llms.txt`. The URLs follow this pattern, shown for Fable 5.2: `https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2.md`. When the guide names an earlier model's guide as its starting point, fetch that one too.
- **Claude Code docs** at `https://code.claude.com/docs/en/<page>.md`, for these pages: `memory`, `settings-reference`, `permissions`, `sub-agents`, `skills`, `hooks`, `permission-modes`, `auto-mode-config`, `model-config`, `advisor`, `commands`. If a page has moved, find it in the docs index at `https://code.claude.com/docs/llms.txt`.

Done when each page is fetched, or listed under "Not checked" with the error. If the live fetch fails, fall back to the `claude-api` skill's bundled guides, and say so in the report.

### 4. Audit the prompt text

Load the `claude-api` skill and follow its `shared/prompt-audit.md`, steps 1–4, over the files from step 2. User-level files are explicitly in scope for this audit. That guide's pattern groups and its keep list are the rulebook here. Apply its keep list as written: cautions that protect real things stay, and so do a user's deliberate verification rules.

If the `claude-api` skill or its `shared/prompt-audit.md` is missing or has changed, follow "If the guide is missing or has changed" above. Whatever the guide's state, cautions that protect real things stay.

Done when every instruction file in the inventory has been scanned against every pattern group.

### 5. Audit the Claude Code configuration

Check each item against the fetched Claude Code docs:

- **Settings:** keys that are unknown or deprecated, and values outside their documented range. Also check model and effort settings, `cleanupPeriodDays`, and permission rules that are broad, shadowed, or in conflict across layers.
- **Hooks:** every hook command resolves to a script that exists and is executable. Every hook event name is a documented one. A `PreToolUse` hook is a **guard** when its inspected script can block a tool call in one of the ways the hooks doc documents: exit code 2, or a `permissionDecision` of `"deny"`. A guard should have `"onFailure": "block"`; without it, the hooks doc says, a failed, timed-out or missing hook is a non-blocking error and the tool call runs. Classify by the script's behavior, not its name. If you can't tell, because the script is unreadable, a binary, or its blocking path isn't clear, say the classification is uncertain and report the missing `onFailure` as a low-confidence note, not as a guard finding.
- **Agent and skill frontmatter:**
  - required fields are present
  - `model` is a documented alias, or a current model ID (flag pinned old IDs)
  - `effort` holds a documented value
  - `tools` names only tools that exist
- **Context load:** compare CLAUDE.md size with what the memory docs say, and verify the figure there instead of assuming it.
- **Skill descriptions:** judge each model-invocable skill's description by its own text. Where it doesn't say when Claude should use the skill, report "Description may not clearly indicate when to use this skill", at low confidence, quoting the description. If the skill is meant to run only when typed, `disable-model-invocation: true` removes its description from every session. Don't infer how or how often a skill is actually invoked; invocation history goes under "Not checked". Also flag descriptions that list synonyms instead of distinct cases.
- **Model routing:** subagents pinned to expensive models for routine work, and work where the docs recommend a different pairing (for example an advisor). Flag these only, with the doc quote.
- **Additions:** text that the prompting guide says to add for an observed behavior, such as finishing work, code ownership or progress updates. Quote the guide's stated costs. When the inspected files establish the prerequisite behavior, make it an `add` finding with a hunk. Otherwise, list it under Recommendations in the report, with the behavior to watch for, and keep it out of the diff.
- **Contradictions:** cases where the user, project and local layers rule differently on the same point. Apply the override test from the prompt-audit guide.

Done when every item has a finding, or a one-word "clean".

### 6. Report and proposed diff

Write the report to `<report-dir>/<project-path-slug>-<YYYY-MM-DD>T<HHMM>Z.md`, with the date and time in UTC, creating the folder if it is missing. `<report-dir>` is:

- the `report-dir=` argument, when one is given; otherwise
- `$SETUP_LINT_DIR`, when it is set; otherwise
- on Linux and macOS, `${XDG_STATE_HOME:-$HOME/.local/state}/setup-lint`
- on Windows, `%LOCALAPPDATA%\setup-lint`

`<project-path-slug>` is the same slug as the auto-memory folder in step 2.

The report quotes user-level files that must not be committed, so it never goes inside a git repository: not the project, and not the config directory when that is version-controlled. The one exception is a folder that its repository ignores, which `git check-ignore -q <report-dir>` confirms. If `<report-dir>` resolves inside a repo that doesn't ignore it, say so in chat and ask where to write instead. Then print the summary and the report's full path in chat.

Report layout:

1. Assumptions: the scope, the target model, and the skipped files
2. A summary: the two or three highest-impact findings in prose, then counts per group
3. The inventory table, with the always-loaded total
4. The references, each with its URL and fetch date
5. The findings, in two sections:
   - **Prompt-text findings** from step 4, in the shape and order of `prompt-audit.md` step 5 (by confidence when that guide is unavailable).
   - **Configuration findings** from step 5, in a section of their own after them, ordered by confidence: every high finding before any medium one, and every medium before any low, whatever their impact. Use the same fields (location, evidence, pattern, why, confidence, action), with the step 5 item it falls under as the pattern. List the items with no finding at the end as "clean" lines, each with at most a short parenthetical reason, such as "(none defined)".
6. Recommendations: suggestions whose prerequisite isn't established, such as conditional additions from step 5, each with what would establish it. None of them go in the diff.
7. The proposed diff: one finding per hunk, high and medium confidence only, grouped by file. Mark each hunk **project** or **user-level**.
8. "Not checked": anything skipped, and why, including any temporary files that couldn't be deleted. End it with the areas this skill doesn't cover: deny rules and sandbox posture, usage and cost data from transcripts (skill invocation history included), and repo readiness. If any `enabledPlugins` entry in the settings files from step 2 starts with `setup-audit@` and is `true`, add that the third-party Setup Audit plugin covers these, and suggest running it read-only: `/setup-audit:setup-audit mode=audit scope=project report_dir=<a folder outside any git repo>`. Don't run it yourself.

Done when the report file exists and the chat summary names its path. Stop there. The person picks which hunks to apply.
